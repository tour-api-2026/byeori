안녕하세요.

관광 데이터 로컬 서버 저장 신청서 안내에 회신드립니다.
저희 팀 **벼리**는 2026 관광데이터 활용 공모전 웹·앱 개발 부문에 참가하고 있으며, 안내해 주신 양식에 따라 신청서를 작성하여 첨부합니다.

**서비스 개요**

벼리는 전국의 관광 명소와 전통 공연·축제를 하나의 지도에서 함께 찾아보고, 하루 여행 일정까지 구성하는 웹 서비스입니다. 현재 아래 주소에서 운영 중입니다.

- 서비스 주소: https://byeori.ernebi.org
- 체험 계정: openapi / 2026openapi!

**데이터 활용 방식**

주요 기능은 로컬 저장에 의존하지 않고 이용자의 요청 시점에 공사 OpenAPI를 직접 호출하도록 구현했습니다.

| 기능 | 오퍼레이션 |
|---|---|
| 지도 주변 탐색 | `locationBasedList2` |
| 명칭 키워드 검색 | `searchKeyword2` |
| 시·도 단위 지역 탐색 | `locationBasedList2` |
| 장소 상세 정보 | `detailCommon2` · `detailIntro2` |

로컬 저장은 실시간 호출로 대체할 수 없는 세 경우에 한정했습니다. 상세한 사유는 첨부한 별지에 정리했습니다.

1. 이용자 관심사 기반 추천 — 자체 보유 평점·리뷰 수로 정렬해야 하는 기능
2. 축소된 전국 화면 — `locationBasedList2`의 반경 상한(20km)을 넘는 구간
3. 공사 API 장애 시 서비스 연속성 확보

**동기화 계획**

공사에서 로컬 서버 저장용으로 제공하시는 `areaBasedSyncList2`를 사용하여 **매일 05:00에 1회** 동기화합니다. 원본 갱신 시각(04:30) 이후가 되도록 설정했습니다.

`modifiedtime`으로 직전 동기화 이후 변경분만 수신하므로 **1회 호출이 약 3건**입니다. 전체 목록을 내려받는 방식(약 350건)에 비해 공사 서버 부담을 크게 줄일 수 있다고 판단했습니다.

또한 응답의 `showflag`가 0인 콘텐츠는 즉시 비노출 처리하여, 공사에서 노출을 중단하신 콘텐츠가 저희 서비스에 남지 않도록 하고 있습니다.

**출처 표기**

장소 상세 화면과 마이페이지의 '데이터 출처' 항목에 `출처: ⓒ한국관광공사`로 표기하고 있으며, API 서비스명을 단독으로 표기하는 방식은 사용하지 않습니다.

**첨부**

1. 관광 데이터 로컬 서버 저장 신청서 (양식)
2. [별지] 신청 사유 및 동기화 계획

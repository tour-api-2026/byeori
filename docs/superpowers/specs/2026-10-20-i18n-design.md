# 다국어 설계 — 한국어·영어·일본어·중국어

외국인이 앱을 열었을 때 **화면도 장소 이름도 모국어로** 보이게 한다.

## 왜

벼리는 외국인 관광객을 겨냥한 앱인데 지금은 전부 한국어다. 화면 문구가 약 500개,
장소 34,728곳과 행사 12,633건의 이름이 모두 한국어뿐이다. 외국인이 설치하면 첫
화면부터 읽을 수 없다.

언어는 **한국어·영어·일본어·중국어(간체)** 네 가지다.

## 무엇을 번역하는가

번역 대상은 세 층으로 갈리고, 층마다 출처와 시점이 다르다.

| 층 | 분량 | 어디에 있나 | 어떻게 |
|---|---|---|---|
| UI 문구 | 약 500개 | 앱 번들 | 사람이 번역해 사전에 넣는다 |
| 서버 메시지 | 사용자에게 보이는 에러 | API 응답 | **앱이 `error.code` 로 번역** |
| **분류값** | **29개** | 서버가 주는 고정 집합 | **앱 사전, 없으면 한국어** |
| 콘텐츠 | 장소·행사 이름, 상세 설명 | DB·공사 API | **AI 로 번역해 DB 에 저장** |

분류값 층은 1단계를 운영에 올린 뒤에 드러났다. 애초 세 층으로 나눌 때 "이름도 설명도
아닌데 서버가 주는 한국어"를 담을 자리가 없었다 — 그래서 어느 단계에도 들어가지 않은 채
외국인이 홈 화면에서 가장 먼저 보는 한국어로 남았다. 자세한 것은 아래 4장.

카테고리(`문화`·`체험`)와 지역(`서울`)은 DB 값이자 화면 라벨이다. **통신 값은 한국어로
두고 표시만 번역한다** — 마이그레이션도 API 변경도 없다.

## 1. i18n 엔진 — 패키지를 넣지 않는다

**이것이 이 설계에서 가장 중요한 제약이다.** `apps/app/package.json` 이 바뀌면 Expo
지문이 달라져 **이미 설치된 앱에 OTA 가 닿지 못한다**(`docs/superpowers/specs/2026-07-19-play-store-ota-design.md`).
`i18next` 를 넣는 순간 다국어는 스토어 재심사를 거쳐야만 사용자에게 간다.

그래서 직접 만든다. 지금 필요한 기능은 치환 하나뿐이다.

```ts
// apps/app/src/lib/i18n/index.ts
export type Locale = 'ko' | 'en' | 'ja' | 'zh';

const DICT: Record<Locale, Record<string, string>> = { ko, en, ja, zh };

/** 현재 언어의 문구. 없으면 한국어로, 그것도 없으면 키를 그대로 돌려준다. */
export function translate(locale: Locale, key: string, vars?: Record<string, unknown>): string {
    const raw = DICT[locale][key] ?? DICT.ko[key] ?? key;
    return raw.replace(/\{(\w+)\}/g, (_, name) => String(vars?.[name] ?? ''));
}
```

화면에서는 훅으로 쓴다. 언어가 바뀌면 다시 그려져야 하므로 스토어를 구독한다.

```ts
const t = useT();
t('route.summary', { km: '3.8', min: '35', n: 4 })   // "3.8km · 약 35분 · 4곳"
```

언어 상태는 `zustand`(이미 의존성), 저장은 `expo-secure-store`(이미 의존성)에 둔다.
계정과 무관하게 **기기에** 저장한다 — 로그인 전에 이미 언어가 정해져 있어야 한다.

### 사전 파일

`apps/app/src/lib/i18n/ko.ts` · `en.ts` · `ja.ts` · `zh.ts`. 키는 화면을 따라
`route.summary`, `routes.empty` 처럼 점으로 나눈다. 네 파일의 키 집합이 어긋나면
조용히 한국어로 떨어진다 — 보이지 않는 고장이다.

**키 목록이 같은지는 검사한다.** 테스트 러너는 못 넣지만(OTA 제약) `node` 스크립트
하나면 된다: `apps/app/scripts/i18n-check.mjs` 가 네 사전의 키 집합을 비교하고,
`translate()` 를 직접 돌려 보고, 이미 번역한 화면에 한국어 리터럴이 남아 있지
않은지 훑는다. 의존성이 없으므로 `package.json` 은 그대로다.

### 기기 언어 감지 — 확인이 필요하다

기본 언어는 기기 설정에서 읽는다. 패키지 없이 되는 길이 두 가지 있다.

1. `Intl.DateTimeFormat().resolvedOptions().locale`
2. React Native 내장 모듈 (`NativeModules.I18nManager` / `SettingsManager`)

**1단계에서 실제 빌드로 확인한다.** 둘 다 안 되면 `expo-localization` 이 필요하고,
그러면 OTA 가 끊겨 스토어 재심사가 된다. 그 경우 **넣을지 말지 사용자에게 묻는다** —
설계가 임의로 정할 일이 아니다. 감지에 실패하면 한국어로 시작한다.

## 2. 언어 선택 UX — 기기 언어를 미리 골라 둔 카드 4개

첫 실행 때 카드 네 장을 띄우되, **감지한 언어를 이미 선택된 상태로** 보여준다.
맞으면 한 번 누르고 지나가고, 아니면 다른 카드를 고른다.

```
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│  한국어   │ │ English  │ │  日本語   │ │  中文    │
│    🇰🇷    │ │    🇺🇸    │ │    🇯🇵    │ │    🇨🇳    │
└──────────┘ └━━━━━━━━━━┘ └──────────┘ └──────────┘
                 ↑ 기기 언어가 en 이라 미리 선택됨
              [  Continue  ]
```

**기기 언어만** 쓰면 영어폰을 쓰는 일본인처럼 어긋나는 사람이 길을 잃는다 — 설정이
한국어로 보이면 바꾸는 곳을 찾지도 못한다. **카드만** 쓰면 대다수에게 불필요한 한
단계이고 어차피 기본값을 정해야 한다. 합치면 추측이 틀려도 그 자리에서 고친다.

**자리는 로그인 화면이 아니라 앱 첫 진입(루트 레이아웃)이다.** 로그인 전에 이미
한국어 화면이 보이기 때문이다. 기존 `onboarding.tsx`(관심 주제·지역)는 **로그인
이후**라 쓸 수 없다.

한 번 고르면 다시 묻지 않는다. 바꾸는 곳은 **마이 → 언어 / Language** 로, 기존
`my/service-info` 옆에 둔다.

## 3. 서버 메시지 — 서버를 건드리지 않는다

응답에 이미 코드가 있다.

```java
public record ErrorBody(String code, String message) {}   // ITINERARY_NOT_FOUND, "여행 일지를 찾을 수 없습니다."
```

앱이 `code` 로 사전을 찾고, **모르는 코드면 서버가 준 한국어 `message` 를 그대로
띄운다.** 새 에러가 생겨도 화면이 비지 않고, 사전에 코드를 더하면 그때부터 번역된다.
서버 Java 의 한국어 408개는 손대지 않는다.

```ts
// 지금:  throw new Error(res.data.error?.message ?? '요청 실패');
// 바뀜:  throw new Error(errorText(res.data.error));   // code → 사전, 없으면 message
```

## 4. 분류값 — 앱 사전으로, 피드 이유만 서버를 고친다

이름도 설명도 아니지만 서버가 한국어로 주는 값들이다. 1단계를 올린 뒤 중국어 화면에서
드러났다 — 틀은 전부 중국어인데 카드 배지 `관심 지역`, 행사 장르 `무용(서양/한국무용)` 이
한국어로 남아 있었다. 외국인이 홈 화면에서 **가장 먼저 보는** 한국어다.

| 분류값 | 가짓수 | 출처 | 처리 |
|---|---|---|---|
| 행사 장르 | 14 | KOPIS 외부 데이터 | 앱 사전 |
| 코스 테마 | 10 | 우리 큐레이션(코스 14건) | 앱 사전 |
| 댓글 태그 | 5 | 우리 DB 테이블 | 앱 사전 |
| 피드 이유 | **10** | **우리 서버가 조립** | **서버를 고친다** |

앞의 셋은 합쳐 29개 키다. 카카오 카테고리에 쓴 방식을 그대로 쓴다 — 사전에 있으면
번역하고, 없으면 **한국어 값을 그대로 보여 준다**. 외부 데이터에 새 장르가 생겨도 화면이
비지 않는다.

### 피드 이유만 서버를 고쳐야 하는 이유

```java
// FeedService.java:264
if (match > 0.5 && v.getCategory() != null) return "관심 주제 · " + v.getCategory();
```

서버가 **문자열을 조립해서** 내려준다. 앱은 `"관심 주제 · 문화"` 를 한 덩어리로 받으므로
사전으로 가를 수 없다. 코드와 값을 나눠 보내고 앱이 합치게 한다.

```
지금:  { "reason": "관심 주제 · 문화" }
바뀜:  { "reason": "FAVORITE_TOPIC", "reasonParam": "문화" }
```

1단계는 "서버를 손대지 않는다"로 갔지만 여기서는 불가능하다. 분기는 열 가지다 —
`venueReason` 이 다섯(내 주변 {km}km · 관심 지역 · 관심 주제 · {분류} · 추천),
`performanceReason` 이 다섯(지금 진행중 · 오늘 시작 · {n}일 뒤 시작 · 관심 주제 · {장르} ·
곧 열리는 행사)이다. 그중 셋은 값을 함께 끼워 넣는다.

`{분류}`·`{장르}` 를 그대로 돌려주는 두 분기는 코드와 값을 나누면 **앱이 이미 가진 분류값
사전을 그대로 탄다** — 따로 번역할 것이 없다.
`reason` 필드의 뜻이 바뀌므로 **앱과 서버를 함께 올려야 한다** — 서버만 먼저 올리면
구버전 앱이 `FAVORITE_TOPIC` 을 그대로 띄운다. OTA 는 머지와 동시에 나가지만 사용자가
앱을 다시 열어야 받으므로, 당분간 둘 다 보내는 편이 안전하다(아래 "내보내는 순서" 참고).

### 큐레이션 코스는 사람이 번역한다

코스 14건의 제목·설명·테마는 공사 데이터가 아니라 우리가 직접 쓴 글이다. AI 배치에
맡길 수도 있지만 **14건뿐이고 루트 탐색 탭 전체가 이것**이라 첫인상을 좌우한다. 사람이
번역하는 쪽이 품질이 낫다. 저장 자리는 장소·행사와 같다(`title_en` 등).

## 5. 콘텐츠 번역 — AI 로 번역해 DB 에 저장한다

### 왜 공사 다국어 서비스가 아닌가

공사 TourAPI 에는 언어별 서비스(`EngService2` 등)가 따로 있다. 공식 번역이라 품질이
보장되고 공모전 명분에도 맞다. 그런데 쓸 수 없는 이유가 쌓여 있다.

| | 공사 다국어 서비스 | **AI 번역 (채택)** |
|---|---|---|
| 매칭 | 국문과 contentId 공간이 다를 가능성 — 같은 장소를 이어 붙일 수단이 불확실 | 우리 행에 컬럼을 더하므로 **매칭 문제가 없다** |
| 커버리지 | 구멍 있음 (영문 축제 0건 보고) | 100% |
| 비용 | 무료 | **일회성 약 $3** |
| 선행 조건 | **TOURAPI 키 복구** — 지금 403 이라 검증조차 못 한다 | 없다 |
| 부수 작업 | 영문은 `contentTypeId` 체계가 달라(관광지 76·축제 85·음식점 82) `CategoryMapper.fromTour` 재작업 | 없다 |

contentId·contentTypeId 에 대한 근거는 공식 문서가 아니라 다른 프로젝트의 이슈
기록이다. **확인하려면 살아 있는 키가 필요한데 지금은 없다.** 키가 403 인 상태
(`SERVICE_KEY_IS_NOT_REGISTERED_ERROR`, 활용신청 반려 2026-09-18 + 기간만료)에서
일정을 키에 묶지 않는 것이 이 선택의 핵심이다.

**나중에 공식 번역으로 덮어쓸 수 있게 설계한다.** 행마다 번역 출처를 남겨
(`tr_source = AI | TOURAPI`) 키가 살아나면 매칭되는 것만 교체하면 된다.

### 분량과 비용

| | 건수 | 이름 평균 | 총 글자 |
|---|---|---|---|
| 장소 | 34,728 | 7자 | 235,899 |
| 행사 | 12,633 | 24자 | 302,109 |

합 538,008자. 3개 언어면 약 160만 자이고, 이미 쓰는 `gpt-4o-mini` 로 **합쳐 $3**
수준이다. 증분은 더 작다 — 장소는 30일에 13건으로 사실상 멈춰 있고, 행사만 주
670건쯤 들어온다(**월 $0.1 미만**).

### 스키마

```sql
ALTER TABLE venues       ADD COLUMN name_en VARCHAR(255),
                         ADD COLUMN name_ja VARCHAR(255),
                         ADD COLUMN name_zh VARCHAR(255),
                         ADD COLUMN name_hash CHAR(64),
                         ADD COLUMN tr_source VARCHAR(10);
-- performances 는 title 에 같은 꼴로
```

필드가 이름 하나뿐이라 별도 번역 테이블은 조인만 늘린다. `name_hash` 는 공사가 이름을
고쳤을 때만 다시 번역하기 위한 것이다 — 이름이 그대로면 영원히 다시 번역하지 않는다.

### 번역 배치

동기화(매일 새벽 5시, `SyncScheduler`) 뒤에 이어 붙인다.

```
동기화 → 새 행·이름 바뀐 행
       → name_en IS NULL OR name_hash <> sha256(name) 인 행을 모아
       → 수백 건씩 묶어 OpenAI 한 번 호출
       → 컬럼에 저장
```

**사용자 요청 경로에는 AI 가 없다.** 앱 요청은 DB 를 읽기만 한다.

품질은 프롬프트에 **국어의 로마자 표기법**과 주요 명소 대조표를 넣어 잡는다
(경복궁 → Gyeongbokgung Palace). 전량을 돌리기 전에 **100건을 뽑아 사용자에게
확인받는다.**

아직 번역되지 않은 행(동기화 직후, 배치 전)은 한국어 이름이 나가고 다음 배치에서
채워진다. 화면이 비는 일은 없다.

### 전달 — Accept-Language

앱이 `Accept-Language` 를 보내고 **서버가 `name` 에 해당 언어를 담아** 내려준다.
모든 언어를 다 내려주면 응답이 세 배가 되고 앱 화면 코드가 전부 바뀐다.

```
GET /venues/nearby        Accept-Language: ja
→ { "name": "景福宮", ... }        // name_ja 가 비면 한국어 name
```

**보내는 값은 우리 `Locale` 네 가지(`ko`·`en`·`ja`·`zh`)를 그대로 쓴다.** `zh-CN`·
`zh-Hans` 같은 BCP-47 꼬리표를 주고받으면 서버가 어느 컬럼을 고를지 또 판정해야 한다.
서버는 아는 네 값이 아니면 한국어로 본다.

앱 쪽은 axios 인터셉터 한 줄이고 화면 코드는 그대로다.

### 검색 — 빼먹으면 안 되는 것

외국인이 `Gyeongbokgung` 으로 검색하면 **지금은 아무것도 나오지 않는다.**
`VenueRepository.search` 가 한국어 `name` 만 본다. 번역 컬럼도 함께 보도록 고쳐야
다국어가 실제로 쓸 만해진다. 이것을 빼면 "번역은 됐는데 검색이 안 되는" 앱이 된다.

### 상세 설명 — 열릴 때 번역하고 저장한다

설명은 DB 에 원문이 없다(34,728곳 중 2곳). 상세 화면이 열릴 때 공사 API 로 실시간
조회하는 값이다. 길어서 매번 번역하면 비싸므로 **그 장소가 처음 열릴 때 번역해
저장하고, 다음부터는 저장분을 쓴다.** 상세는 조회 빈도가 낮아 이쪽이 맞다.

## 6. AI 루트는 번역하지 않는다

`AiRouteService.systemPromptNew()` 에 언어를 넘기면 처음부터 그 언어로 만들어진다.
번역 단계도 추가 비용도 없다.

## 단계

각 단계는 끝나면 그 자체로 쓸 수 있다.

| 단계 | 내용 | 끝나면 |
|---|---|---|
| 1. 뼈대 | `t()`·언어 스토어·저장, **기기 언어 감지 확인**, 첫 실행 카드 4개, 마이의 언어 항목 | 언어를 바꾸면 그 화면들이 실제로 바뀐다 |
| 2. UI 문구 | 약 500개를 화면 단위로 추출 | 앱 전체가 4개 언어 |
| 3. 서버 메시지 | `error.code` 사전 | 에러도 모국어로 |
| 4. 분류값 | 사전 29키 + 피드 이유 서버 분리 | 홈 화면에서 한국어가 사라진다 |
| 5. 콘텐츠 | 스키마 + 번역 배치 + `Accept-Language` + **검색** | 이름이 모국어로, 로마자 검색도 된다 |
| 6. 마무리 | 설명 lazy 번역·저장, 큐레이션 코스 수동 번역, AI 루트 언어 지정 | 완결 |

1~3단계는 끝났다(PR #88, 운영 반영). 4단계부터가 이 다음 계획이다.

2단계는 화면 단위라 나누어 진행하기 좋다. 문구가 가장 많은 쪽은 `ai-route`(60),
`venue/register`(58), `itinerary/[id]`(35), `onboarding`(33) 이다.

## 시험

백엔드는 Gradle 테스트로 덮는다 — 번역 배치의 대상 선별(`name_hash` 비교), 응답의
언어 선택(`Accept-Language` → 어느 컬럼), 번역 컬럼을 포함한 검색.

**앱에는 테스트 러너를 둘 수 없다**(`package.json` 이 바뀌면 OTA 가 끊긴다). 대신
`apps/app/scripts/i18n-check.mjs` 를 둔다 — 의존성 없는 `node` 스크립트로 세 가지를
본다.

1. 네 사전의 **키 집합이 같은지**
2. `translate()` 가 키 없음·변수 없음 같은 경우에 어떻게 떨어지는지
3. 이미 번역한 화면에 **한국어 리터럴이 남아 있지 않은지**

순수 함수의 본문은 `.ts` 파일에서 떼어내 타입 표기만 지우고 돌린다 — 경로 날짜
분할(`splitByDay`)을 검증할 때 쓴 방법이고, 실제 코드를 돌리므로 베끼면서 어긋날
일이 없다.

## 열어 둔 것

- **기기 언어 감지**가 패키지 없이 되는지. 1단계에서 확인하고, 안 되면 OTA 를 끊고
  `expo-localization` 을 넣을지 사용자에게 묻는다.
- **번역 품질**. 4단계 전량 배치 전에 100건을 뽑아 확인받는다.
- **공사 다국어 서비스**는 TOURAPI 키가 살아난 뒤에 별도로 검토한다. 그때
  `tr_source` 가 있어 교체가 가능하다.
